# 작업 지시서 — 관리자 백엔드 (김성원 · 임지연)

> **브랜치:** `feature/backend-phase2` (이미 origin에 생성되어 있음, main과 동일 상태 — 그대로 사용)
> **참고 문서:** `docs/백엔드_기능명세.md` — Module A~H 전체 코드 스펙이 여기 있음. 이 지시서는
> "누가 어떤 순서로 착수하는지"만 정리한 것이므로, 각 모듈 착수 전 반드시 명세서의 해당 섹션을 정독한다.
> **역할 분배:** 김성원 — 마이그레이션·인증·메뉴관리·회원관리 / 임지연 — 주문로직·주문관리·쿠폰할인·결제환불·통계
>
> 기존 명세서 4절 "담당자 배정 표"는 진수민 단독 배정으로 되어 있었으나, 이번에 김성원·임지연
> 두 명이 나눠 진행하는 것으로 변경한다(아래 배정이 최신 기준).

## 시작 전 확인 (둘 다)

- [ ] `git checkout feature/backend-phase2` (origin에서 pull, 로컬에 없으면 `git checkout -b feature/backend-phase2 origin/feature/backend-phase2`)
- [ ] `docs/백엔드_기능명세.md` 전체를 한 번 읽는다 — 0절(현재 상태), 0-1절(공통 구현 규칙)은 모듈 상관없이 공통 적용
- [ ] 로컬 `kiosk_db`에 접속 가능한지 확인 (마이그레이션 완료 후 ALTER TABLE을 각자 직접 실행해야 함)

**공통 규칙 (명세서 0-1절 요약, 반드시 준수):**
- DAO는 `commit()` 호출 금지 — `flush()`까지만, 커밋은 라우터에서
- 에러는 전부 `HTTPException(status_code, detail="한국어 문장")`
- `/api/admin/*` 라우터는 예외 없이 `Depends(get_current_admin)` (또는 `require_owner`)를 라우터 생성 시점에 건다
- 시각 필드는 `.isoformat()` 문자열로 직렬화

## 진행 순서 (의존관계 — 이 순서를 벗어나면 막힘)

```
1단계 (김성원, 선행 — 임지연도 대기)   1-A/1-B/1-D 마이그레이션 + 의존성 추가
2단계 (병렬)                        김성원: Module A(인증)   ×   임지연: Module C(주문로직 버그수정)
3단계 (병렬, 2단계 완료 후)          김성원: Module B(메뉴관리) ×  임지연: Module E(주문관리)
4단계 (병렬)                        김성원: Module G(회원관리) ×  임지연: Module F(쿠폰·할인)
5단계 (임지연만, C·E·A 모두 완료 후)  임지연: Module D(결제·환불)
6단계 (임지연만, 마지막)             임지연: Module H(통계)
```

커밋은 모듈 단위로 나누고 이슈 번호를 남긴다 (예: `feat(admin): 관리자 인증 구현 (#22)`).
같은 브랜치를 공유하므로 **1단계 완료 후 반드시 push, 임지연은 pull 받은 뒤 2단계 착수**.

## 임지연 담당 — Module C · Module E · Module F · Module D · Module H

### Module C. 주문 처리 로직 보완 (최우선 — 이미 매출 데이터에 영향 주는 버그)

- [ ] **push 후 완료 알림 — 김성원의 Module G, 자신의 Module F가 이 함수들에 의존**

### Module E. 주문 관리 (관리자)

> 착수 조건: 김성원의 Module A(인증) 완료 후

- [ ] `backend/api/admin/orders.py`, `order_dao.py`에 `list_orders`/`update_order_status` 추가

- [ ] 완료 기준: 결제 완료 주문이 `RECEIVED`로 즉시 조회 / 앞으로만 전이 가능 / `CANCELLED`는 예외적으로 항상 허용

### Module F. 쿠폰·할인 관리자 CRUD

> 착수 조건: 자신이 만든 Module C의 쿠폰 로직 완료 후 (선행 조건 자체 충족)

- [ ] 완료 기준: 쿠폰 생성 후 `code`로 주문 시 정상 적용 / `max_usage_count` 도달 시 추가 발급·사용 불가

### Module D. 결제·환불 관리

> 착수 조건: **Module C(본인) + Module E(본인) + Module A(김성원) 모두 완료 후** — 세 모듈 함수를 그대로 호출하므로 순서상 가장 나중

- [ ] `backend/api/admin/payments.py`, `payment_dao.py`에 `get_payment_by_order_id`/`list_payments`/`mark_refunded` 추가
- [ ] 환불 처리 흐름 — 명세서의 코드 그대로: `adjust_points`로 포인트 원상복구(적립분 회수 + 사용분 반환) → `user_coupon_id` 있으면 `restore_coupon` → `mark_refunded` + `update_order_status(CANCELLED)`
- [ ] **★ 환불은 Module E의 `_is_valid_transition` 검증을 거치지 않고 `update_order_status`를 직접 호출** — 완료된 주문도 환불 가능해야 하므로 의도적으로 별개 경로
- [ ] `current_points`가 음수로 내려가는 것은 이번 범위에서 허용(포인트 부채) — 하한 체크 넣지 않음
- [ ] 완료 기준: 환불 시 결제·주문·포인트·쿠폰 동시 정확히 원상복구 / 이미 환불된 결제 재환불 시도 시 409

### Module H. 통계·대시보드 (맨 마지막)

> 착수 조건: Module C, E 완료 — 주문 상태·항목 데이터가 정확해야 통계가 의미 있음

- [ ] `backend/api/admin/stats.py`, `backend/dao/stats_dao.py`, `backend/schemas/stats_schemas.py` 생성
- [ ] 집계는 `status='COMPLETED'` 건만 대상(취소·환불 제외) — 단순 `SUM`/`GROUP BY` 수준으로 충분, 별도 배치/집계 테이블 만들지 않음
- [ ] 완료 기준: 매출 합계가 실제 `COMPLETED` 주문 합과 일치 / 환불 건은 집계에서 제외
