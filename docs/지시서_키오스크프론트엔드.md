# 작업 지시서 — 일반 키오스크 프론트엔드 (조예성, PM 본인)

> 11개 화면 자체는 이미 구현되어 있다(README 진행 현황 체크 완료). 이 문서는 "새 화면을 만드는 일"이
> 아니라, **실제 백엔드(DB API)와 연결했을 때 깨지는 지점 + 아직 UI가 없는 기능**을 정리한 것이다.
> 코드를 직접 훑어서 확인한 현재 상태 기준이며, 관리자 백엔드(`docs/지시서_관리자백엔드.md`) 진행
> 상황에 따라 일부 항목은 순서를 조정한다.

---

## 0. 왜 이 작업이 필요한가

지금까지 프론트는 `VITE_API_URL` 미설정 시 정적 데이터로 동작하도록 만들어져 있어(`services/*.js`의
`if (API_BASE) {...} return {...}` 분기), 실제 서버 없이도 화면 개발이 가능했다. 하지만 이 분기 안의
**API 계약(엔드포인트 경로·응답 필드명)이 실제 백엔드 스펙과 어긋나는 부분**이 있다 — 지금 붙이면
바로 에러가 난다. 아래는 코드를 직접 대조해서 찾은 불일치 목록이다.

---

## 1. API 계약 불일치 수정 (최우선)

### 1-A. `pointsService.js` — 존재하지 않는 엔드포인트를 호출하고 있음

`frontend/src/services/pointsService.js`는 `GET /api/points/lookup?phone=`, `POST /api/points/add`를
호출하도록 되어 있는데, 실제 백엔드(`backend/api/user.py`)에는 이 두 엔드포인트가 **아예 없다**.
있는 건 `GET /api/user/points/{phone}` (`UserPointsOut` 반환, 필드: `user_id/phone_number/current_points/tier`)뿐이고, **고객 이름(`name`) 필드 자체가 DB/스키마 어디에도 없다.**

`CartScreen.jsx`의 "안녕하세요, {이름}님" 표시는 이 존재하지 않는 이름 필드에 의존하고 있으므로
결정이 필요하다:

- [ ] **(권장)** 이름 표시를 포기하고 일반 문구로 변경 — 예: "안녕하세요, 회원님" 또는 등급(`tier`)만 표시. `pointsService.js`를 `GET /api/user/points/{phone}` 호출로 교체, `lookupCustomer` 반환값에서 `name` 제거
- [ ] (대안, 백엔드 수정 필요) 회원 이름 표시를 유지하고 싶다면 진수민(Module G 담당)과 상의해 `User` 모델에 `name`/`nickname` 필드 + 조회 API 추가 요청 — 이번 스코프에는 없으므로 별도 협의 필요
- [ ] `addPoints()` — 실제로는 별도 적립 API가 없다. `POST /api/orders`의 `phone` 파라미터로 주문 시점에 적립이 자동 처리되므로(Module C), **결제 완료 후 별도로 `addPoints()`를 호출할 필요 자체가 없어질 수 있음** — Module C 완료 후 `CartScreen.jsx`의 `handleComplete()`에서 `addPoints` 호출 제거 여부 결정

### 1-B. `orderService.js` — 응답 필드명 불일치

`createOrder()`가 `{ orderNum, orderId }`를 기대하지만, 실제 `POST /api/orders` 응답(`OrderOut`)은
`{ order_id, order_number, ... }`(스네이크케이스 + 필드명 자체가 다름)이다.

- [ ] `orderService.js`의 `createOrder()`에서 응답을 `{ orderNum: data.order_number, orderId: data.order_id }`로 매핑해서 반환하도록 수정 (호출부인 `CartScreen.jsx`는 그대로 둬도 되게)
- [ ] `getOrderStatus()`도 동일하게 실제 응답(`order_id`/`order_number`/`status`) 기준으로 매핑 확인 — 현재 어느 화면에서도 호출되지 않는 죽은 코드이니 당장 급하진 않지만, 나중에 쓸 때를 위해 주석의 스펙을 실제 스펙으로 고쳐둘 것

### 1-C. `paymentService.js` — 응답 필드명 불일치

`processPayment()`가 `{ success, transactionId }`를 기대하지만, 실제 `POST /api/payments` 응답
(`PaymentOut`)은 `{ payment_id, order_id, method, amount, status, paid_at }`이다 — `success`/
`transactionId` 필드 자체가 없다.

- [ ] `paymentService.js`에서 `status === 'SUCCESS'`를 `success`로, `payment_id`를 `transactionId`
      대용으로 매핑
- [ ] 결제 실패 시(`status !== 'SUCCESS'`, 또는 400 에러 응답의 `detail` — 9af4882 커밋에서 상세
      사유 반환하도록 이미 개선됨) `CardPaymentScreen`/`CashPaymentScreen`/`PayPaymentScreen` 쪽에서
      에러 메시지를 어떻게 보여줄지 확인 (`CartScreen.jsx`의 `handleComplete` catch 블록이 현재
      `console.error`만 하고 사용자에게 아무 표시도 안 함 — 최소한 결제 실패 안내 팝업 필요)

**완료 기준 (1절 전체):**
- [ ] `.env`에 `VITE_API_URL` 설정한 상태로 메뉴 조회 → 장바구니 담기 → 포인트 조회 → 결제 →
      주문 생성까지 전 과정이 실제 백엔드 응답으로 끊김 없이 동작
- [ ] 결제 실패 시 사용자에게 실패 사유가 화면에 표시됨(현재는 콘솔에만 찍힘)

## 2. 쿠폰 입력 UI 신규 추가

`backend`의 `OrderIn` 스키마에는 `coupon_code` 필드가 있고(관리자 백엔드 Module C·F에서 처리 로직
구현 중), 프론트에는 **쿠폰 코드를 입력할 곳이 아예 없다** — `CartScreen.jsx`의 `createOrder()` 호출에
`coupon_code`가 전달되지 않는다.

- [ ] `CartScreen.jsx`의 결제 흐름에 쿠폰 입력 단계 추가 — 기존 포인트 적립 팝업(전화번호 입력)과
      유사한 흐름으로, "쿠폰 있으신가요?" → 코드 입력 → 할인 적용된 금액 표시 후 결제 진행
      (UI 디자인은 `docs/지시서_관리자UI디자인.md`의 쿠폰 화면과 별개 — 고객용 키오스크 쪽 쿠폰 입력
      UI는 이 문서 범위이므로 직접 디자인 겸 구현)
- [ ] `orderService.js`의 `createOrder()` 파라미터에 `couponCode` 추가, `OrderIn.coupon_code`로 전달
- [ ] 쿠폰 적용 실패 시(만료/이미 사용/최소주문금액 미달 등, Module C가 400 에러로 상세 사유 반환)
      에러 메시지를 그대로 화면에 노출
- **착수 조건:** `docs/지시서_관리자백엔드.md`의 Module C(임지연 담당, 쿠폰 적용 로직) 완료 후 —
  임지연에게 완료 여부 확인 후 통합 테스트
