# 백엔드 기능 명세 및 업무 분배 (Phase 2 — 일반 사용자 흐름 보완 + 관리자 화면 신규)

> **목적:** Phase 1(`DB_파트_작업명세.md`, `AI_파트_작업명세.md` — #15~#19)에서 만든 것은
> "메뉴 조회 → 장바구니 → 음성 주문" 까지의 기본 파이프라인이다. 그 과정에서 처리하지 않고
> 남겨둔 백엔드 로직(포인트 적립, 쿠폰 적용, 주문 상태 등)과, 지금까지 전혀 없던 **관리자 화면**을

> **전제:** 관리자 화면(프론트엔드)도 별도로 제작한다고 가정한다. 이 문서는 그 화면이 호출할
> **백엔드 로직·API**를 정의하는 것이 목적이며, 관리자 프론트엔드 UI 자체는 다루지 않는다.

## 0-1. 공통 구현 규칙 (모든 모듈이 지켜야 함)

이 프로젝트는 Alembic 같은 마이그레이션 툴을 쓰지 않는다(`backend/core/db.py`의 `init_db()`가
`Base.metadata.create_all`만 호출). **신규 환경(테이블이 아예 없는 상태)에서는 `models.py`만
고치면 자동으로 반영되지만, 이미 테이블이 만들어진 로컬/개발 DB에는 `create_all`이 컬럼을
추가해주지 않으므로 본문에 적어둔 `ALTER TABLE`을 직접 실행해야 한다.** 각 모듈 담당자는
자기 컴퓨터의 `kiosk_db`에 해당 ALTER를 실행했는지 반드시 확인한다.

- **DAO는 절대 `commit()`하지 않는다.** `flush()`까지만 하고 커밋은 호출한 API 라우터가
  한다(기존 DB 파트 규칙과 동일, `docs/DB_파트_작업명세.md` 참고).
- **에러 응답 포맷은 전부 동일하게** `HTTPException(status_code, detail="한국어 메시지")`.
  `detail`은 그대로 화면에 노출/음성 안내될 수 있으므로 항상 사람이 읽는 한국어 문장으로 쓴다.
- **`/api/admin/*` 라우터는 예외 없이 인증이 걸려야 한다.** 라우터를 만들 때 개별 엔드포인트마다
  `Depends`를 붙이는 대신, 아래처럼 라우터 생성 시점에 한 번만 걸어 빠뜨리는 사고를 막는다
  (Module A가 `get_current_admin`/`require_owner`를 만들면 이후 모듈은 import만 해서 쓴다):
  ```python
  # backend/api/admin/orders.py 등 — 로그인만 요구하는 라우터
  router = APIRouter(
      prefix="/api/admin/orders", tags=["admin-orders"],
      dependencies=[Depends(get_current_admin)],
  )

  # OWNER 전용 라우터(예: 관리자 계정 관리를 나중에 추가한다면)
  router = APIRouter(..., dependencies=[Depends(require_owner)])
  ```
  `/api/admin/auth/login`은 예외(로그인 자체는 인증 없이 호출해야 하므로 별도 라우터로 분리하거나
  해당 엔드포인트에만 의존성을 걸지 않는다).
- **관리자 API 응답의 시각(datetime) 필드는 모두 ISO 8601 문자열**(`str(dt)` 또는
  `dt.isoformat()`)로 직렬화한다 — 기존 `PaymentOut.paid_at` 처리 방식과 동일하게 통일.

## 1. 데이터 모델 변경 사항

### 1-A. `orders.status` 컬럼 추가 (신규 마이그레이션 — 최우선)

`backend/core/models.py`의 `Order`에 상태 컬럼이 아예 없다. 관리자 주문 관리·고객 주문 조회
양쪽 모두 이 컬럼이 있어야 성립하므로 가장 먼저 처리한다.

```python
# backend/core/models.py — Order 클래스에 추가
status: Mapped[str] = mapped_column(
    SAEnum("RECEIVED", "COOKING", "READY", "COMPLETED", "CANCELLED", name="order_status"),
    default="RECEIVED",
)
# 환불 시 포인트·쿠폰을 정확히 원상복구하려면 "이 주문에 어떤 쿠폰을 썼는지"가 남아있어야 한다.
# discount_amount 만으로는 역산이 불가능하므로 참조를 직접 저장한다.
user_coupon_id: Mapped[str | None] = mapped_column(
    String(36), ForeignKey("user_coupons.id"), nullable=True
)
```

`database/init.sql`에도 동일하게 `orders` 테이블 정의에 `status`, `user_coupon_id` 컬럼을
추가한다(팀 전체가 SQL로도 초기화하므로 스키마 두 곳 반드시 동기화). 이미 서비스 중인 DB가 있다면
`ALTER TABLE orders ADD COLUMN status ENUM(...) NOT NULL DEFAULT 'RECEIVED', ADD COLUMN user_coupon_id VARCHAR(36) NULL;`로 마이그레이션.

상태 흐름: `RECEIVED`(결제 완료, 접수) → `COOKING`(조리 중) → `READY`(픽업 대기) →
`COMPLETED`(수령 완료). `CANCELLED`는 언제든 전이 가능(환불 발생 시 함께 처리, Module D 참고).

### 1-B. 관리자 계정 — `AdminUser` 신규 테이블

고객용 `users` 테이블(비회원 세션, 포인트, 접근성 설정)과 관리자 계정은 목적이 완전히 다르므로
**별도 테이블로 분리**한다(권한·감사로그가 붙는 계정 개념을 고객 테이블에 얹으면 나중에 꼬인다).

```python
# backend/core/models.py — 신규 클래스
class AdminUser(Base):
    __tablename__ = "admin_users"

    id: Mapped[str] = mapped_column(String(36), primary_key=True, default=_uuid)
    username: Mapped[str] = mapped_column(String(64), unique=True)
    password_hash: Mapped[str] = mapped_column(String(255))
    display_name: Mapped[str] = mapped_column(String(64))
    role: Mapped[str] = mapped_column(
        SAEnum("OWNER", "STAFF", name="admin_role"), default="STAFF"
    )
    is_active: Mapped[bool] = mapped_column(Boolean, default=True)
    last_login_at: Mapped[datetime | None] = mapped_column(DateTime, nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime, server_default=func.now())
```

`OWNER`는 전체 기능(계정 관리 포함), `STAFF`는 주문/메뉴 관리만 — 세부 권한 분기는 Module A에서
FastAPI Depends로 처리(라우터 단위로 role 체크).

### Module C. 주문 처리 로직 보완 — 최우선, 기존 버그 수정

**담당:** _(TBD)_ · **선행 조건:** 1-A(orders.status 컬럼) 완료 후 착수

일반 사용자 흐름에서 이미 매출 데이터에 영향을 주는 버그이므로 관리자 화면보다 먼저 고친다.

**대상 파일:** `backend/api/order.py`, `backend/dao/order_dao.py`, `backend/dao/user_dao.py`

1. **주문 항목 직렬화 누락** — `backend/api/order.py`의 `create_order`가 `OrderOut.items`에
   항상 빈 배열(`items=[]`)을 반환한다(`# 필요 시 items 직렬화 추가`라고 주석 처리만 되어 있음).
   `order_with_items`(이미 조회해서 변수까지 만들어 두고 안 씀)의 `items`를 `OrderItemOut`으로
   변환해 채워야 한다.

2. **포인트 미반영** — `points_earned`를 계산만 하고 `User.current_points`에 실제로 더하지
   않는다. `points_to_use`도 마찬가지로 차감되지 않는다. `user_dao.py`에 다음 함수 추가:
   ```python
   async def adjust_points(db: AsyncSession, user_id: str, delta: int) -> None:
       """delta 는 양수(적립)/음수(차감) 모두 가능. commit 은 라우터에서."""
       user = await db.get(User, user_id)
       if user:
           user.current_points += delta
   ```
   `order.py`의 `create_order`에서 `body.phone`으로 `get_user_by_phone` 조회 → 존재하면
   `adjust_points(db, user.id, points_earned - points_to_use)` 호출 후 커밋. 비회원(전화번호 없음)은
   포인트 적립/차감 자체를 생략(현재 동작 유지).

3. **쿠폰 적용 로직 미구현** — `# TODO: 쿠폰 적용 로직 추가` 그대로 방치되어 있다.
   `body.coupon_code`와 `body.phone`이 모두 있으면(쿠폰은 회원 전용 — 비회원은 스킵):
   - 해당 회원에게 발급된 미사용 `user_coupons` 중 `coupons.code == body.coupon_code`인 행을
     조회(`user_dao.py`에 `get_user_coupon_by_code(db, user_id, code)` 추가) → 없거나 이미
     `is_used=True`면 400 에러
   - `coupons.is_active=False`이거나 `min_order_amount` 미달 시 400 에러
   - `discount_type`이 `PERCENT`면 `subtotal * discount_value / 100`, `CASH`면 `discount_value`를
     `discount_amount`로 반영
   - 적용 성공 시 아래 함수로 `user_coupons`/`coupons` 갱신:
     ```python
     # user_dao.py 추가
     async def mark_coupon_used(db: AsyncSession, user_coupon_id: str) -> None:
         """is_used=True, used_at=now(). 연결된 coupons.used_count += 1. commit 은 라우터에서."""

     async def restore_coupon(db: AsyncSession, user_coupon_id: str) -> None:
         """mark_coupon_used 의 반대 동작 — is_used=False, used_at=None, coupons.used_count -= 1.
         Module D(환불)에서 사용."""
     ```
   - **★ 1-A에서 추가한 `Order.user_coupon_id`에 이 `user_coupons.id`를 반드시 저장** — 안 저장하면
     Module D의 환불 시 쿠폰 복구가 불가능해진다.

4. **주문 상태 반영** — `GET /api/orders/{order_id}`가 `{"status": "completed"}` 리터럴을
   반환하던 것을 1-A에서 추가한 실제 `order.status` 값으로 교체.

**응답 스키마 변경** — `backend/schemas/order_schemas.py`의 `OrderOut`에 `status: str` 필드 추가
(이미 있는 `order_id/order_number/order_type/subtotal/discount_amount/final_amount/points_used/points_earned/items`는 유지):

```python
class OrderOut(BaseModel):
```

**완료 기준**
- [ ] `POST /api/orders` 응답의 `items`가 실제 담긴 메뉴 목록과 일치

      적용된 쿠폰이 저장되며, 같은 쿠폰 재사용 시 400 에러(`is_used=True`라서 재적용 불가)

**`backend/core/security.py`** (비밀번호 해시 + JWT 발급/검증 — 다른 모듈은 이 파일의
`get_current_admin`/`require_owner`만 import해서 쓰면 된다):
```python
import os
from datetime import datetime, timedelta

from fastapi import Depends, HTTPException
from fastapi.security import OAuth2PasswordBearer
from jose import JWTError, jwt
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"])
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/admin/auth/login")

_SECRET = os.getenv("ADMIN_JWT_SECRET", "dev-only-insecure-secret")
_EXPIRE_MIN = int(os.getenv("ADMIN_JWT_EXPIRE_MINUTES", "480"))

def hash_password(raw: str) -> str:
    return pwd_context.hash(raw)

def verify_password(raw: str, hashed: str) -> bool:
    return pwd_context.verify(raw, hashed)

def create_access_token(admin_id: str, role: str) -> tuple[str, int]:
    expire = datetime.utcnow() + timedelta(minutes=_EXPIRE_MIN)
    payload = {"sub": admin_id, "role": role, "exp": expire}
    token = jwt.encode(payload, _SECRET, algorithm="HS256")
    return token, _EXPIRE_MIN * 60

async def get_current_admin(token: str = Depends(oauth2_scheme)) -> dict:
    """반환값: {"id": admin_id, "role": role}. main.py 의존성 주입 체인에서 DB 세션 없이
    토큰만으로 검증 — 계정 활성 여부까지 매 요청 확인하려면 admin_dao 조회를 추가해도 된다."""
    try:
        payload = jwt.decode(token, _SECRET, algorithms=["HS256"])
        return {"id": payload["sub"], "role": payload["role"]}
    except JWTError:
        raise HTTPException(401, "인증 정보가 유효하지 않습니다. 다시 로그인해 주세요.")

async def require_owner(admin: dict = Depends(get_current_admin)) -> dict:
    if admin["role"] != "OWNER":
        raise HTTPException(403, "관리자(OWNER) 권한이 필요합니다.")
    return admin
```

환불은 "이 주문 자체가 없었던 것"으로 되돌리는 작업이므로, Module C에서 주문 시 반영한

```python
# backend/api/admin/payments.py — refund 핸들러 내부 흐름
payment = await db.get(Payment, payment_id)
if payment is None:
    raise HTTPException(404, "결제 내역을 찾을 수 없습니다")
if payment.status == "REFUNDED":
    raise HTTPException(409, "이미 환불된 결제입니다")

order = await get_order_by_id(db, payment.order_id)

# 1) 포인트 원상복구: 주문 시 반영했던 델타의 정확히 반대 방향으로 되돌린다.
#    (Module C: adjust_points(delta=points_earned - points_to_use) 를 호출했던 것과 대칭)
#    → 적립해준 포인트는 회수하고, 차감했던 포인트(사용분)는 돌려준다.
if order.user_id:
    await adjust_points(db, order.user_id, -(order.points_earned - order.points_used))

# 2) 쿠폰 원상복구: 이 주문에 쓰인 쿠폰이 있으면 다시 사용 가능하게 되돌린다.
if order.user_coupon_id:
    await restore_coupon(db, order.user_coupon_id)   # is_used=False, used_at=None, coupons.used_count -= 1

# 3) 결제·주문 상태 전이
#    ★ 여기서는 Module E의 _is_valid_transition 검증을 거치지 않고 order_dao.update_order_status를
#    직접 호출한다. 그 검증은 관리자가 PATCH /orders/{id}/status로 수동 전이할 때만 적용되는
#    규칙이고("완료된 주문은 취소 불가"), 환불은 완료 이후에도(다음날 고객이 환불을 요청하는 등)
#    항상 가능해야 하는 별개의 관리 동작이기 때문이다.
await mark_refunded(db, payment.id, reason)
await update_order_status(db, order.id, "CANCELLED")
await db.commit()
```

(`restore_coupon`은 Module C에서 이미 정의해뒀다 — 여기서는 import만 해서 쓴다.)

**포인트 적립분과 사용분을 이미 회원이 다른 주문에서 다시 써버렸으면 어떻게 되나?**
`current_points`가 음수로 내려갈 수 있다. 이번 스코프에서는 **음수를 허용**한다(포인트 부채로

- [ ] 환불 처리 후 `Payment.status=REFUNDED`, `Order.status=CANCELLED` 동시 반영

**상태 전이 검증 알고리즘** (`update_order_status` 호출 전 라우터에서 체크):

```python
_ORDER = ["RECEIVED", "COOKING", "READY", "COMPLETED"]   # 인덱스가 클수록 나중 단계

def _is_valid_transition(current: str, new: str) -> bool:
    if new == "CANCELLED":
        return current != "COMPLETED"          # 완료된 주문은 취소 불가(환불은 별도 정책)
    if current == "CANCELLED":
        return False                            # 취소된 주문은 어디로도 못 감
    if current not in _ORDER or new not in _ORDER:
        return False
    return _ORDER.index(new) > _ORDER.index(current)   # 앞으로만, 여러 단계 건너뛰기는 허용
```
`COOKING`을 건너뛰고 `RECEIVED → READY`로 바로 넘기는 것은 허용(간단한 음료 단독 주문 등
실제 조리 단계가 없는 경우가 있어 매장 운영상 자연스럽다). 단, 뒤로 가는 전이는 항상 400.

**★ 이 검증은 `PATCH /api/admin/orders/{id}/status`(관리자가 손으로 상태를 넘기는 경우)에만
적용된다.** Module D의 환불 처리는 이 검증을 거치지 않고 `order_dao.update_order_status`를
직접 호출해 `COMPLETED` 상태에서도 `CANCELLED`로 전이한다 — 완료된 주문도 환불은 가능해야
하므로 의도적으로 별개 경로다. `order_dao.update_order_status` 자체에는 전이 규칙을 넣지 않고,
검증(`_is_valid_transition`)은 Module E의 API 라우터 레이어에만 둔다.

**완료 기준**
- [ ] 새 주문 결제 완료 시 관리자 목록에 `RECEIVED` 상태로 즉시 조회됨
- [ ] `RECEIVED → COOKING → READY → COMPLETED` 순서로 앞으로만 전이 가능(중간 단계 건너뛰기는
      허용, 역행은 항상 400)
- [ ] `CANCELLED`는 `COMPLETED`가 아닌 모든 상태에서 전이 가능(환불 처리 경로 포함)

| POST | `/api/admin/coupons/{id}/issue` | `{phone: str}` → `UserCouponOut` (해당 회원에게 발급) |
| GET | `/api/admin/discounts` | 목록 → `list[DiscountOut]` |
| POST | `/api/admin/discounts` | 할인 생성 (`DiscountIn`) → `DiscountOut` |
| PATCH | `/api/admin/discounts/{id}` | 활성화 여부 등 수정 → `DiscountOut` |

**응답/요청 스키마** (`backend/schemas/coupon_schemas.py`):

```python
class CouponIn(BaseModel):
    code: str
    discount_type: str            # CASH | PERCENT
    discount_value: Decimal
    min_order_amount: Decimal = Decimal("0")
    max_usage_count: int = 0      # 0 = 무제한
    valid_from: date | None = None
    valid_until: date | None = None

class CouponOut(CouponIn):
    id: str
    used_count: int
    is_active: bool

class UserCouponOut(BaseModel):
    user_coupon_id: str
    user_id: str
    coupon_id: str
    issued_at: str

class DiscountIn(BaseModel):
    target_type: str              # MENU | CATEGORY | ALL
    menu_item_id: str | None = None
    category_id: str | None = None
    discount_type: str            # CASH | PERCENT
    discount_value: Decimal
    name_ko: str
    name_en: str
    valid_from: date | None = None
    valid_until: date | None = None
    applicable_tier: str = "ALL"  # ALL | STUDENT | SENIOR | GOLD

class DiscountOut(DiscountIn):
    id: str
    is_active: bool
```

**`DiscountIn` 검증 규칙** (라우터에서 체크, 안 지키면 400):
- `target_type="MENU"` → `menu_item_id` 필수, `category_id`는 `None`이어야 함
- `target_type="CATEGORY"` → `category_id` 필수, `menu_item_id`는 `None`이어야 함
- `target_type="ALL"` → 둘 다 `None`이어야 함

**참고:** `Discount`는 현재 주문 계산 로직 어디에서도 조회되지 않는다. 이 모듈에서 관리자 CRUD를
만든 뒤, Module C의 주문 생성 로직에 "적용 가능한 discount 조회 → subtotal에 반영"을 추가하는
후속 작업이 필요하다(이 문서 범위에서는 CRUD까지만; 자동 적용 로직은 별도 이슈로 분리 권장).

**완료 기준**
- [ ] 쿠폰 생성 후 `code`로 사용자 주문(Module C) 시 정상 적용
- [ ] `max_usage_count` 도달한 쿠폰은 추가 발급/사용 불가

## 3. 우선순위 및 작업 순서 제안

```
1순위 (선행, 병렬 불가)  1-A (orders.status 마이그레이션), 1-B (AdminUser 마이그레이션)
2순위 (병렬 가능)        Module C (주문 로직 버그 수정)  ×  Module A (관리자 인증)
3순위 (Module A 완료 후) Module B (메뉴 관리) · Module E (주문 관리) · Module G (회원 관리)  — 병렬 가능
4순위                   Module D (결제·환불) · Module F (쿠폰·할인)
5순위 (데이터 누적 후)   Module H (통계)
```

**근거:** Module C는 이미 실서비스 매출 데이터 정합성 문제(포인트 미반영 등)이므로 관리자 화면보다
먼저 고친다. Module A는 나머지 모든 관리자 모듈의 전제조건이라 그 다음. Module H는 정확한
주문 상태·항목 데이터가 쌓인 뒤에야 의미가 있으므로 가장 나중.

> **현재 배정 (갱신):** 김성원·임지연 2인이 나눠서 진행한다 — 김성원: 1-A/1-B 마이그레이션 ·
> Module A(인증) · Module B(메뉴관리) · Module G(회원관리) / 임지연: Module C(주문로직) ·
> Module E(주문관리) · Module F(쿠폰·할인) · Module D(결제·환불) · Module H(통계). 위 "병렬 가능"
> 표현이 실제로 적용되는 배정이다. 세부 순서·의존관계는 `docs/지시서_관리자백엔드.md` 참고.

## 5. 통합 테스트 시나리오 (전 모듈 완료 후, 순서대로 실행)

로컬에서 `uvicorn main:app`을 띄운 뒤 아래 순서로 확인한다. `TOKEN`은 로그인 응답의
`access_token`, `Authorization: Bearer $TOKEN` 헤더를 이후 모든 `/api/admin/*` 요청에 포함한다.

1. `POST /api/admin/auth/login` (부트스트랩 계정) → 200, `access_token` 수신
2. `GET /api/admin/auth/me` (토큰 없이) → 401
3. `GET /api/admin/auth/me` (토큰 포함) → 200, 로그인한 계정 정보
4. `POST /api/admin/menu/items` 로 테스트 메뉴 1개 생성 → `GET /api/menu`(고객용, 인증 불필요)에서
   바로 조회되는지 확인
5. `PATCH /api/admin/menu/items/{id}` 로 `is_available=false` → 음성 주문 시나리오("이 메뉴
   주세요")에서 "품절" 응답으로 이어지는지 확인 (`invalidate_cache()` 연동 확인)
6. `POST /api/admin/coupons` 로 쿠폰 생성 → `POST /api/admin/coupons/{id}/issue`로 테스트
   회원(전화번호)에게 발급
7. 고객 플로우로 장바구니 담기 → `POST /api/orders`에 `phone`+`coupon_code` 포함 →
   `discount_amount` 정확히 계산되는지, 응답의 `items`가 채워지는지 확인
8. `GET /api/user/points/{phone}` → 적립 포인트 반영 확인
9. `GET /api/admin/orders?status=RECEIVED` → 방금 만든 주문이 조회되는지 확인
10. `PATCH /api/admin/orders/{id}/status` 로 `COOKING → READY → COMPLETED` 순서로 전이
11. `GET /api/admin/stats/summary` → 방금 주문의 `final_amount`가 매출에 반영됐는지 확인
12. **환불 시나리오:** 위 주문을 `POST /api/admin/payments/{id}/refund`로 환불 →
    - `GET /api/user/points/{phone}` 포인트가 주문 이전 값으로 정확히 복귀
    - 발급했던 쿠폰이 다시 미사용 상태(재발급/재사용 가능)로 복구
    - `GET /api/admin/stats/summary` 매출에서 해당 주문 제외
