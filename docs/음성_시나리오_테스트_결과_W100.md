## 4. 검증

- **단위 테스트 63개 통과**(기존 51 + 신규 12, `tests/test_cart_commands.py`): 명령 문법 분류, 문법 밖 발화 오탐 없음, 직전 기록, 옵션 근거 범위, 여러 턴 세트.
- **오프라인 오탐 점검**: 고정 100개의 모든 발화(1,122개)를 새 파서에 넣어, 명령 문법 조작(되돌리기·다시 담기·세트 담기·변환·옵션 변경·수량 줄이기)만 분류되고 담기·삭제·수량 지정·결제 등은 하나도 걸리지 않음.
- LLM 실측은 1절 표와 같다.

실행하며 만든 회귀 두 건은 같은 날 고쳤다: ① 포인트 질문 보강이 "적립 안 할게요" 턴에서도 동작해 정상 응답을 덮어씀 → 이번 턴에 처음 시작한 결제에만 적용. ② "옵션을 묻는 중" 판정을 좁히다 질문 뒤에 문장이 이어지는 경우를 놓침 → 질문 문장이 하나라도 있으면 해당.

3차 보강 요지(3차 측정의 실패 6개): ① 모델이 `update_item_options`에 `item_type="single"`을 같이 넘기면 수량 보정이 건너뛰어짐 → 이미 단품인 줄이면 수량 변경으로 취급.
② 장바구니에 이미 있는 버거를 "X 하나 줘"라고 하면 단품/세트를 묻지 않고 수량을 올리거나 "이미 담겨 있습니다"라고 함 → 수량 변경 차단(`set_update_instead_of_add`)과
질문 보강(`single_set_question_missing`), 이어지는 "단품으로 줘"는 직전 손님 발화가 단품/세트 없는 버거 주문이면 담음. ③ 여러 메뉴를 말한 발화에서는 `menu_mismatch`로
id를 자동 보정하지 않음(한 메뉴가 2개+1개로 중복). ④ 수량을 늘린 메뉴를 같은 턴에 `add_item`으로 또 담는 호출 무시(`add_after_update`).

## 5. 남은 문제

1. **3차 보강 후 100개 전체 재측정 1회**(필요할 때만, 비용). 가드 개입 표에서 `direct_command`·`set_followup_completed`·`points_question_missing`의 개별 사유를 읽어 오탐 여부 점검.
2. **모델 변동**: W029("새우버거 단품 빼줘"에 액션 없이 "빼지 못했어요")처럼 같은 발화가 실행마다 다르게 처리됨. 삭제도 직접 명령으로 옮길 수 있으나(줄 하나로 정해질 때) 아직 하지 않음.
3. **`start_checkout` 중복 호출**: 포인트에 답한 턴에 모델이 `start_checkout`을 다시 부르는 로그가 보임(`['points','start_checkout']`). 화면이 포인트 팝업을 다시 띄울 수 있다. 실기기 확인 필요.
4. **직접 명령은 한국어 전용**(`language`가 ko/미지정일 때만). 영어·일본어 문법은 없다.
5. **직접 명령의 화면 반영은 실기기에서 확인 못 함**: 백엔드 장바구니는 즉시 바뀌고 `add_item`/`update_item`/`remove_item` 액션으로 프런트가 새로고침하는 구조(`App.jsx` `execAppAction`)를 따랐지만 화면에서는 보지 못했다.
6. 비용: 이번 작업의 LLM 실행은 전체 100개 3회 + 44개 1회 + 개별 재실행 약 35개. 전체 실행 한 번이 약 1시간(workers 3~4).
7. 위 3절 이후 코드는 커밋하지 않았다.

## 6. 후속 작업 (2026-10-03 오후)

- **temperature 0.2 → 0** (`ai_modules/llm/agent.py`). 같은 시드에서 0.2와 비교한 적은 없어 효과는 미측정.
- **랜덤 30개(시드 2026)**: 28/30. 실패 2개 중 R2026-24는 삭제 기록이 마지막 줄만 남던 결함(`cart_history`를 턴 단위 목록으로 수정, 서버가 같은 옵션의 줄을 합치지 않으므로 줄이기·삭제도 여러 줄 처리),
  R2026-21은 "양념감자튀김"을 말했는데 "감자튀김(M)"을 맞다고 보던 `_mentions_other_menu`의 부분 문자열 결함(발화에서 읽힌 메뉴 이름을 긴 이름 먼저 비교하도록 수정). 수정 후 R2026-21 통과, R2026-24는 `ReadTimeout`.
- **`localhost` 지연**: 이 Windows PC에서 `localhost`로 새 연결을 만들면 약 2초, `127.0.0.1`은 15~30ms. 가드·도구가 `API_BASE_URL`로 내부 API를 여러 번 부르므로 직접 처리 턴이 3.0~3.2초 → 0.2~0.9초로 줄었다.
  `api_client.py` 기본값과 `start_servers.ps1`을 `127.0.0.1`로 변경(Linux·Pi에서도 안전).
- **응답 시간 집계**: `python tools/latency_report.py out.json ...` — 가드 개입 분류(direct/blocked/fixed/none)별 평균·중앙값·P95. 수정 전 측정(1,461턴, workers 3): 직접 처리 중앙값 3.2초, LLM 턴 5.0초, 가드 거절 턴 +4.1초.
- **힌트 + 재질의**(`backend/core/order_hints.py`): 파서가 확신하는 단순 주문이면 모델 입력 뒤에 `add_item(menu_item_id=<UUID>, quantity=N)`를 제안한다. 모델이 담지 않으면 빠진 품목만 짚어 한 번 더 질의하고(`hint_requery`), 그래도 안 되면 기존 코드 보완이 이어받는다.
  실제 앱의 스트리밍 경로는 힌트 대상 턴만 내부적으로 비스트림 실행 후 최종 문장을 한 번에 보낸다.
  - 8개 시나리오(W003 W009 W016 W017 W094 W096 W099 W100) 8/8 통과. 같은 시나리오에서 가드 개입: `id_is_name` 8→2, `simple_order_completed` 4→0, `menu_mismatch` 1→0, 거절 개입 2→0. 힌트를 따른 턴 14, **재질의는 한 번도 발생하지 않아 재질의 경로는 실제 LLM으로 검증되지 않았다**(단위 테스트는 힌트 구성만).
  - 턴 평균 5.3초 → 2.1초는 `localhost` 수정과 섞여 있어 힌트만의 효과로 볼 수 없다.
  - 표본이 8개뿐이라 일반화하지 말 것. 힌트를 넣은 뒤 100개 전체는 재측정하지 않았다.
