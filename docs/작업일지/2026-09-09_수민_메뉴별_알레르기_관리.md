# 개발 작업일지

- 작성일: 2026년 9월 9일
- 작성자: 수민
- 작업 주제: 관리자 메뉴별 알레르기 관리 및 LLM 연동 기반 구성
- 작업 브랜치: `feature/menu-allergy-management`

## 1. 작업 목적

음성으로 키오스크를 이용하는 사용자가 메뉴의 알레르기 유발물질을 질문했을 때, AI가 데이터베이스에 등록된 정보를 바탕으로 안내할 수 있도록 메뉴별 알레르기 관리 기반을 구성하였다.

알레르기 정보는 키오스크의 일반 메뉴 화면에 직접 노출하는 기능이 아니라, 관리자가 메뉴별 정보를 등록하고 LLM이 메뉴를 설명하거나 알레르기 관련 질문에 답할 때 활용하는 것을 목적으로 한다.

## 2. 수행한 작업

### 기존 데이터 구조 조사

- 엑셀, CSV 등 별도의 메뉴 정리 파일이 있는지 프로젝트 전체를 확인하였다.
- 실제 메뉴 초기 데이터가 `backend/core/seed.py`와 `database/init.sql`에 저장되어 있음을 확인하였다.
- 이미 알레르기 유발물질 19종을 저장하는 `allergens` 테이블과 메뉴-알레르기 다대다 관계를 저장하는 `menu_item_allergens` 테이블이 구현되어 있음을 확인하였다.
- 메뉴 API와 LLM의 RAG 검색 로직이 메뉴별 `allergens` 데이터를 읽을 수 있도록 일부 구현되어 있음을 확인하였다.

### 관리자 메뉴 수정 화면 개선

- 관리자 페이지의 메뉴 추가·수정 모달 하단에 알레르기 유발물질 19종 체크 영역을 추가하였다.
- 한 메뉴에 여러 알레르기 항목을 동시에 선택할 수 있도록 구현하였다.
- DB에 기존 매핑값이 있는 경우 메뉴 수정 화면에서 해당 항목이 미리 체크되도록 하였다.
- 프론트엔드의 알레르기 코드가 DB 코드와 정확히 일치하도록 대문자 표준 코드로 통일하였다.

### DB 저장 기능 및 LLM 연동

- 메뉴 생성 및 수정 요청 스키마가 `allergen_codes` 목록을 받을 수 있도록 확장하였다.
- 관리자가 저장하면 해당 메뉴의 기존 알레르기 관계를 삭제하고 새 선택값으로 교체하도록 DAO 로직을 추가하였다.
- 존재하지 않는 알레르기 코드가 전달되면 잘못된 데이터가 저장되지 않도록 검증을 추가하였다.
- 메뉴 정보가 변경된 뒤 LLM 메뉴 검색 캐시를 무효화하여 이후 질의부터 변경된 정보가 반영되도록 하였다.

### 현재 메뉴의 초기값 정리

- 현재 등록된 메뉴 26개와 알레르기 초기 매핑 26개가 일치하는지 검사하였다.
- 메뉴 설명의 주요 재료를 기준으로 버거와 사이드 메뉴의 개발용 초기 체크값을 구성하였다.
- 음료와 감자튀김처럼 설명만으로 표시 대상 성분을 확인할 수 없는 메뉴는 체크하지 않고 별도 검토 대상으로 남겼다.
- 조장과 메뉴 담당자가 실제 레시피 및 제품 성분표를 확인할 수 있도록 `docs/메뉴별_알레르기_초기값_검토요청.md`를 작성하였다.

## 3. 작업 중 어려웠던 점

### 메뉴 데이터의 기준 위치가 명확하지 않았음

처음에는 메뉴와 원재료가 엑셀 파일에 정리되어 있을 것으로 예상했지만 프로젝트에는 엑셀이나 CSV 파일이 없었다. 메뉴 데이터가 SQL 초기화 파일, Python 시드 파일, 프론트엔드의 레거시 정적 데이터에 나뉘어 있어 실제 운영 기준을 구분하는 과정이 필요했다.

조사 결과 현재 시스템에서는 DB가 실제 데이터의 기준이며, `backend/core/seed.py`는 초기 DB를 구성하는 역할이고 `frontend/src/data/menuData.js`는 일부 세트 표시 기능에 남아 있는 레거시 데이터임을 확인하였다.

### 화면 구현과 실제 저장 기능이 분리되어 있었음

관리자 화면에 체크박스를 추가하는 것만으로는 LLM이 정보를 사용할 수 없다. 체크값이 API 요청에 포함되고, 백엔드 스키마를 통과하여, 메뉴와 알레르기의 다대다 관계 테이블에 저장된 후, 다시 메뉴 API와 LLM 검색 데이터로 전달되어야 했다.

따라서 프론트 화면만 수정하지 않고 요청 스키마, API, DAO, DB 관계, LLM 캐시까지 전체 데이터 흐름을 추적해야 했다.

### 프론트엔드와 DB의 알레르기 코드 형식이 달랐음

초기 체크 UI에서는 `egg`, `milk`와 같은 소문자 코드를 사용했지만 DB에는 `EGG`, `MILK`와 같은 대문자 코드가 저장되어 있었다. 이 상태에서는 DB에 값이 있어도 관리자 화면에서 기존 선택값이 체크되지 않는다. 프론트엔드 코드를 DB 표준과 동일하게 변경하여 문제를 해결하였다.

### 기존 DB에서는 초기 알레르기 값이 입력되지 않을 수 있었음

기존 시드 로직은 메뉴가 하나라도 존재하면 즉시 종료되었다. 따라서 이미 운영 중인 DB에 알레르기 테이블이 새로 추가되어도 메뉴별 초기 매핑이 비어 있을 수 있었다.

이를 해결하기 위해 알레르기 마스터 19종 중 누락된 항목을 보충하고, 메뉴-알레르기 매핑 테이블 전체가 비어 있을 때만 현재 메뉴의 초기값을 한 번 채우도록 보완하였다. 관리자가 수정한 값이 서버 재시작 때 반복적으로 덮어써지지 않도록 조건을 제한하였다.

### 로컬 실행 환경과 배포 환경을 구분해야 했음

로컬 관리자 페이지를 실행했지만 백엔드가 실행되지 않아 로그인 요청이 실패했고, `.env` 파일은 보안상 Git에 포함되지 않기 때문에 클론만으로 DB 비밀번호와 API 키가 복사되지 않았다. 이후 로컬 프론트에서 배포 백엔드를 사용하도록 `VITE_API_URL`을 설정하여 화면 확인 환경을 구성하였다.

다만 로컬에서 변경한 백엔드 코드는 배포 전까지 실제 서버에 적용되지 않는다. 이번 기능을 실제 배포 DB에서 사용하려면 브랜치를 병합·배포하고 백엔드를 재시작해야 한다.

## 4. 해결 과정에서 배운 점

- UI 기능은 화면만 구현해서 끝나는 것이 아니라 데이터가 생성되고 소비되는 전체 경로를 확인해야 한다.
- 다대다 관계는 메뉴 행에 문자열을 직접 저장하는 방식보다 별도 마스터 테이블과 연결 테이블을 사용하는 것이 수정과 확장에 유리하다.
- 프론트엔드와 백엔드는 동일한 식별 코드 규칙을 사용해야 기존 값 조회와 수정이 안정적으로 동작한다.
- 시드 데이터는 신규 DB뿐 아니라 기존 DB에 기능을 추가하는 상황도 고려해야 한다.
- 알레르기 정보는 안전과 직접 관련되므로 설명만으로 추정한 값을 확정 정보처럼 제공하면 안 된다.

## 6. 남은 작업

- 조장 또는 메뉴 담당자가 실제 레시피와 납품 제품의 성분표를 기준으로 초기값 검토
- 소스, 패티, 튀김옷, 시즈닝에 포함된 세부 알레르기 성분 확인
- 공용 튀김유와 조리 기구로 인한 교차접촉 안내 정책 결정
- 기능 브랜치 병합 및 서버 배포
- 배포 DB에서 관리자 체크값 저장·재조회 확인
- 음성 질의로 메뉴별 알레르기 안내가 정확히 출력되는지 통합 테스트

## 7. 논문 작성 시 활용 가능한 내용

본 작업은 음성 기반 배리어프리 키오스크에서 식품 안전 정보를 제공하기 위한 데이터 관리 구조로 설명할 수 있다. 관리자가 메뉴별 알레르기 유발물질을 구조화된 형태로 입력하면 LLM이 자연어 질의에 답할 때 이를 근거 데이터로 활용한다.

LLM이 메뉴 설명만 보고 알레르기 정보를 임의로 추론하도록 하지 않고, 관리자가 검증한 DB 값을 검색 증강 생성(RAG) 과정에 제공한다는 점이 중요하다. 이를 통해 환각 가능성을 낮추고, 메뉴 정보가 변경되어도 관리자 페이지에서 데이터를 수정하여 안내 내용을 갱신할 수 있다.

다만 DB에 등록되지 않은 성분이나 조리 과정의 교차접촉 가능성까지 완전히 보장할 수는 없다. 따라서 시스템은 “안전하다”라고 단정하기보다 등록된 알레르기 유발물질을 고지하고, 필요한 경우 직원 또는 공식 성분표 확인을 권고하는 방식으로 설계해야 한다.
