# 작업 지시서 — 관리자 페이지 UI 디자인 (김명서 · 진수민)

> **목적:** 관리자 백엔드(`docs/지시서_관리자백엔드.md`, Module A~H)가 완성되면 이를 호출할
> 관리자 웹 화면이 필요하다. 이 문서는 그 화면들의 **디자인 시안(Figma)** 제작 범위를 정의한다.
> 실제 프론트엔드 코드 구현은 별도 이슈 — 이번 작업은 디자인까지만.
>
> **진수민은 관리자 백엔드(Module A/B/G)도 함께 맡고 있으므로, UI 디자인은 3화면만 배정한다.**
> **착수 조건:** 없음 — 백엔드 API 완성을 기다릴 필요 없이 바로 시작 가능(각 모듈 명세서에 응답
> 필드가 이미 정의되어 있어 화면에 표시할 데이터는 확정되어 있음).

## 0. 공통 원칙

- **기존 키오스크 디자인 시스템을 그대로 계승한다** — 완전히 새로운 톤을 만들지 않는다.
  - 메인 브라운 `#744032` (헤더/포인트), 포인트 레드 `#e00` (강조/주문번호), 옐로우 `#F5B800` (보조 CTA), 배경 `#f5f5f5`
  - 폰트: Pretendard
  - 참고: `frontend/figmasample/` 폴더의 기존 키오스크 화면 PDF/이미지 (시작화면, 메뉴화면, 결제화면 등)
- **디바이스 기준:** 관리자 화면은 키오스크(세로/터치)와 달리 **데스크톱·태블릿 가로 화면** 기준으로 디자인한다 (매장 직원이 PC 또는 태블릿으로 사용).
- **컴포넌트 재사용 전제로 디자인:** 목록 테이블, 상태 배지(뱃지), 필터 바, 모달 폼 등 화면마다 반복되는 패턴은 공통 컴포넌트로 통일해서 그린다(화면마다 다르게 그리면 나중에 프론트 구현 비용이 커짐).
- **각 화면에 표시해야 할 데이터 필드는 아래 표의 "표시 데이터" 열을 그대로 따른다** — 이 필드들은 `docs/백엔드_기능명세.md`에 정의된 실제 API 응답 스키마에서 그대로 가져온 것이므로 임의로 필드를 빼거나 새 필드를 지어내지 않는다. 화면에 없었으면 하는 필드가 있으면 디자인 전에 PM(조예성)과 상의.
- **산출물:** Figma 파일 1개(공유 링크), 팀 Notion에 화면별 캡처 첨부. 완성된 화면마다 "완료" 태그 남기기.

## 2. 화면별 상세 스펙

### 화면 1. 로그인 (김명서)

- **표시 데이터:** 아이디, 비밀번호 입력 필드
- **상태:** 기본 / 에러(`"아이디 또는 비밀번호가 올바르지 않습니다"` 문구 노출)
- 로그인 성공 시 대시보드로 이동하는 흐름만 명시(화면 전환은 프론트 구현 시 처리)

### 화면 2. 대시보드 / 통계 (김명서)

- **표시 데이터:** 오늘 매출 합계, 오늘 주문 건수, 평균 객단가(`StatsSummaryOut`) / 최근 7일·30일 매출 추이 꺾은선 또는 막대 그래프(`SalesSeriesOut`) / 인기 메뉴 랭킹 리스트(`PopularItemOut` — 메뉴명, 판매수량, 매출)
- 기간 필터(7일/30일) UI 필요
- 로그인 후 첫 진입 화면이므로 사이드바 내비게이션(주문관리/메뉴관리/쿠폰관리/회원관리/결제관리로 이동) 포함해서 설계

### 화면 3. 주문 관리 (김명서)

- **표시 데이터(목록):** 주문번호, 주문유형(매장/포장), 상태(`RECEIVED`/`COOKING`/`READY`/`COMPLETED`/`CANCELLED`), 결제상태, 금액, 생성시각
- **표시 데이터(상세):** 주문 항목 목록(메뉴명·수량·옵션·특이사항), 결제 정보
- **인터랙션:** 상태 필터(전체/미완료만 기본), 상태 변경 버튼 — **상태는 앞으로만 전이 가능**(예: RECEIVED→COOKING→READY→COMPLETED, 중간 단계 건너뛰기는 허용하되 역행은 버튼 자체를 비활성화하는 디자인 권장), CANCELLED는 완료 전이면 언제든 가능
- 실시간 갱신은 폴링 방식(수 초 간격 자동 새로고침) 전제 — "마지막 갱신 시각" 같은 작은 표시 고려

### 화면 4. 결제·환불 관리 (김명서)

- **표시 데이터:** 결제ID, 연결 주문번호, 결제수단, 금액, 상태(`PENDING`/`SUCCESS`/`FAILED`/`REFUNDED`), 실패사유, 결제시각, 환불시각
- **인터랙션:** 상태/기간 필터, "환불" 버튼 → 환불 사유 입력 팝업 → 확인
- 환불은 되돌릴 수 없는 동작이므로 확인 팝업에 "포인트·쿠폰이 함께 원상복구됩니다" 같은 안내 문구 포함 권장
- 이미 `REFUNDED` 상태인 건은 환불 버튼 비활성화

### 화면 5. 메뉴·카테고리 관리 (진수민)

- **표시 데이터:** 카테고리 목록(이름, 노출여부, 순서) / 메뉴 목록(이름, 가격, 품절여부, 인기여부, 신메뉴여부, 카테고리) / 메뉴별 옵션 목록(이름, 추가금액, 노출여부)
- **인터랙션:** 카테고리·메뉴·옵션 각각 생성/수정/삭제(삭제는 진행 중 주문에 포함된 메뉴는 소프트 삭제만 가능하므로, 삭제 버튼 클릭 시 "삭제 대신 품절 처리됩니다" 같은 안내가 나올 수 있음을 감안해 설계)
- 이미지 업로드 UI 필요(메뉴 이미지)
- 품절 토글은 목록에서 바로 켜고 끌 수 있게(모달 진입 없이) — 매장에서 빠르게 써야 하는 기능

### 화면 6. 쿠폰·할인 관리 (진수민)

- **표시 데이터(쿠폰):** 코드, 할인유형(정액/정률), 할인값, 최소주문금액, 사용횟수/최대사용횟수, 유효기간, 활성여부
- **표시 데이터(할인):** 적용대상(메뉴/카테고리/전체), 할인유형, 할인값, 이름, 유효기간, 적용등급, 활성여부
- **인터랙션:** 쿠폰 생성/수정, 특정 회원(전화번호)에게 쿠폰 발급, 할인 생성/수정
- 쿠폰 발급은 "회원 검색 후 발급" 흐름으로 설계(화면 7의 회원 검색 UI와 패턴 통일)

### 화면 7. 회원·포인트 관리 (진수민)

- **표시 데이터(목록):** 전화번호, 현재 포인트, 등급, 회원가입일, 비회원 여부
- **표시 데이터(상세):** 최근 주문 내역(화면 3 주문 목록과 동일한 카드/행 컴포넌트 재사용), 보유 쿠폰 목록
- **인터랙션:** 전화번호로 검색, 포인트 수동 조정(증감값 + 사유 입력 — 사유는 필수 입력이라 빈 채로 제출 불가하게 디자인)

## 3. 진행 순서 제안

1. 김명서: 공통 레이아웃(사이드바/헤더) + 화면 1(로그인) 먼저 확정 → 진수민에게 공유
2. 병렬: 김명서는 화면 2-4, 진수민은 화면 5-7 (공통 레이아웃 프레임 복제해서 사용)
3. 완료 후 서로의 화면을 한 번씩 교차 검토(디자인 톤 통일 여부 확인) — 특히 상태 배지 색상(RECEIVED/COOKING/READY/COMPLETED/CANCELLED, PENDING/SUCCESS/FAILED/REFUNDED)은 화면 3·4에서 같은 색상 규칙을 써야 하므로 김명서가 먼저 정의하고 진수민 화면에도 동일 적용
