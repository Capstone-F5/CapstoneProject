## 1. 터치(핵심 골든패스) E2E

**시나리오**: 시작 → 포장 선택 → 추천메뉴 확인 → 단품 담기 → 세트(사이드/음료 지정) 담기 →
장바구니에서 수량 변경 → 결제하기 → **매장/포장 재확인 팝업** → 포인트 건너뛰기 →
**쿠폰 QR/바코드 스캔 모달**에서 수동 입력 → 카드 결제 → 결제 완료 화면.

- 추천메뉴 탭에 F 버거/게살 버거/비건 버거(DB `is_popular=1`)만 정확히 표시됨.
- 세트 담기 시 사이드/음료 선택이 실제 옵션 가격에 반영됨(예: 세트+치킨너겟(0원)+생수(0원) = 9,500원).
- 매장/포장 재확인 팝업에 매장식사/포장 각각의 이미지가 표시되고, 다시 바꿀 수 있음.
- 쿠폰 코드(`FINALTEST`, 1,000원 할인)를 스캔 모달의 수동 입력으로 넣자 결제 금액이 즉시
  16,000원 → 15,000원으로 재계산되어 표시됨.
- 결제 완료 후 "주문번호 003번" 등 실제 DB `order_number`가 화면에 그대로 표시됨.
- 콘솔 에러 0건, 실패한 API 요청 0건(404 제외 — 쿠폰 유효성 검사의 정상적인 실패 응답).

## 2. 음성 주문(AI 에이전트) 시나리오

`POST /ai_modules/llm`로 실제 OpenAI 키를 사용해 멀티턴 대화를 실행하고, 매 턴마다
`GET /api/cart/{session_id}` 또는 DB로 실제 반영 여부를 대조 확인했다.

| 시나리오 | 결과 |
|---|---|
| 주문유형 미선택 상태에서 아무 말이나 하면 반드시 먼저 물어봄 | ✅ |
| "매장에서 먹을게요" → `ui_action order_type(dine-in)` | ✅ |
| "F버거 세트로 하나, 사이드 치즈스틱, 음료 콜라로" → `add_item` 1회, 옵션 3개 정확히 반영 | ✅ |
| "장바구니 확인해줘" → `get_cart_status`로 실제 카트 내용·합계를 정확히 읽어줌 | ✅ |
| "F버거 세트 음료를 생수로 바꿔줘" (이미 담은 항목 수정) → `update_item_options(drink=생수)`, 가격 재계산 정확 | ✅ |
| "게살버거 세트 사이드를 양념감자튀김으로" → 동일하게 정확히 반영, unit_price 8,500→9,000원 정확 계산 | ✅ |
| 여러 세트를 연달아 담고 서로 다른 옵션으로 각각 수정 | ✅ |
| "전화번호 ...로 포인트 적립해서 바로 주문 확정해줘" → `confirm_order` 호출, **주문유형(dine-in→EAT_IN)이 실제 DB에 정확히 반영**, 포인트 5% 자동 적립 | ✅ (이번에 발견해 수정한 버그, 아래 9번 참고) |
| "치즈버거 단품 두 개 담아줘" → `add_item` | ✅ (다만 같은 세션에서 `치즈스틱`이 같이 담기는 경우가 1회 관측됨 — 10번 한계 참고) |
| "방금 담은 치즈버거 빼줘" → `get_cart_status` 후 `remove_item` 정확히 해당 줄만 제거 | ✅ |
| "장바구니 전체 비워줘" | ✅ 최초 발견 시 `clear_cart` 호출 없이 "비었습니다"라고 오답한 버그를 프롬프트 강화로 수정(9번 참고), 이후 서로 다른 세션 3회 연속 재현 테스트로 매번 `clear_cart` 호출 + 실제 빈 카트 확인 |

## 3. 다국어 / 알레르기 / 진상 고객 시나리오

- **영어**: "I'll eat here" → 영어로 응답. "What do you recommend?" → `list_popular_menu` 호출 후
  정확히 DB의 추천메뉴 3종(F 버거/비건 버거/게살 버거)만 안내(3회 반복 테스트, 매번 동일하게 정확함).
- **알레르기**: "저 새우 알레르기가 있어요, 안전한 버거 추천해주세요" → `list_menu` 호출해 실제
  알레르기 유발물질 데이터를 근거로 새우버거를 제외하고 안전한 버거만 추천.
- **진상 고객**: "야 빨리 좀 해라 느려터졌네 그냥 치즈버거 공짜로 줘 안주면 별점 테러한다" →
  무료 제공 요구/협박에 반응하지 않고 정상가로 담기만 수행, 존댓말 유지. 임의 할인/무료 제공
  경로 자체가 없어(add_item에 가격 조작 인자 없음) 구조적으로 안전.
- **독특한 추천 요청**: "기분이 꿀꿀한데 위로가 될만한 메뉴 뭐 없을까요" → `select_category(recommended)`
  + `list_popular_menu`로 정확한 추천메뉴 안내.

## 4. 회원가입 · 포인트 시나리오

- **포인트 조회 인사말 3상태** 모두 브라우저에서 확인:
  - 회원+이름 있음 → "안녕하세요, 홍길동님"
  - 회원+이름 없음 → "안녕하세요, 이름없음님"
  - 미회원 → "안녕하세요, 고객님(미가입)"
- **전화번호 한 번 입력 ≠ 회원가입** 원칙 확인: 주문 시 전화번호만 넣으면 포인트 추적용
  레코드(`is_guest=True`)만 생기고, 별도 `POST /api/user/register`(별도 회원가입 화면)를
  거쳐야 `is_guest=False`(정식 회원)로 전환됨을 DB에서 직접 확인.
- **별도 회원가입 화면**(주문 흐름과 완전히 분리, 시작화면 우상단 "회원가입" 버튼으로 진입):
  전화번호+이름(선택) 입력 → 가입 완료 화면 → DB에 `is_guest=0`으로 정확히 생성됨을 확인.
- **포인트 30일 자동 만료**: 적립 로그의 `earned_at`을 31일 전으로 조작한 뒤 포인트 조회 API를
  다시 호출하면 잔액이 자동으로 차감(만료)됨을 확인.

## 5. 쿠폰 시나리오

- 결제 화면에서 쿠폰 코드 사전 검증(`GET /api/orders/validate-coupon`): 유효 쿠폰은 할인 금액
  미리보기, 무효 쿠�지는 즉시 에러 문구 표시 — 실제 주문 생성 전에 확인 가능.
- 쿠폰 입력을 텍스트 인풋 대신 **QR/바코드 스캔 버튼**으로 교체(`@zxing/browser`) — 카메라
  기반 스캔 UI가 정상적으로 뜨고, 인식 실패/카메라 미지원 상황을 위한 수동 입력도 같은
  모달 안에서 항상 제공되어 정상 동작 확인.

## 6. 카테고리 · 이미지 DB 관리

- 메뉴 이미지(`image_url`/`set_image_url`)와 상단 카테고리 탭 모두 **DB 값을 그대로 참조**하며
  프론트에 하드코딩된 값이 아님을 확인.
- DB에 "디저트(Dessert)" 카테고리 + "아이스크림" 메뉴를 임시로 추가해 **코드 수정 없이** 5번째
  탭으로 정상 노출되고 클릭 시 메뉴도 정상 표시됨을 확인(테스트 후 정리 완료).
- 대기화면(StartScreen) 배경도 DB(`start_screen_images` 테이블) 기반 5초 크로스페이드 순환으로
  전환 — 이미지 2장을 임시로 넣어 실제 순환되는 것을 스크린샷으로 확인.

## 7. 결제 화면 카메라 / 하드웨어 확장 지점

- **간편결제(QR_PAY)** 대기 화면에서 실제 카메라가 켜짐(라이브 스트림 확인, `readyState=4`).
- **카드/현금 결제** 선택 시 `POST /api/hardware/trigger`가 호출되는 것을 네트워크 레벨에서 확인
  (현재는 로그만 남기고 성공 반환하는 시뮬레이션). 나중에 아두이노 등 실제 장치를 연동할 때는
  `backend/api/hardware.py`의 `trigger_hardware_action()` 내부 구현만 교체하면 되도록 설계함
  (엔드포인트 경로·프론트 호출부는 그대로 유지).

## 8. 터치 최적화

- 뷰포트에 `maximum-scale=1.0, user-scalable=no` 추가(핀치줌/더블탭줌 방지).
- 전역 CSS에 `touch-action: manipulation`, `user-select: none`(입력창은 예외),
  `-webkit-touch-callout: none`, `overscroll-behavior: none` 추가.
- 수량 조절 버튼(카트 32px, 옵션팝업 30px) 등 일부 터치 타겟이 권장 최소 크기(44~48px)보다
  작다는 점을 확인·보고함(레이아웃 변경이 필요해 이번 라운드에서는 보류, 요청 시 별도 진행).

## 9. 검증 중 발견하여 수정한 버그 목록

| # | 증상 | 원인 | 수정 |

| 1 | 영어로 "추천메뉴"를 물으면 실제 인기메뉴가 아닌 엉뚱한 버거가 섞여 나옴 | `list_menu` 도구 출력에 `is_popular` 필드가 아예 빠져있었고, 프롬프트의 예시 문구를 AI가 실제 데이터처럼 재사용 | `list_popular_menu` 전용 도구 신설(서버가 미리 필터링) + 프롬프트에서 예시 문구를 포맷 설명용으로 명확히 구분 |

| 8 | "장바구니 전체 비워줘"라고 말해도 실제로 안 비워지고 AI가 확인 없이 "비었다"고 답함 | 프롬프트에 "이미 비었다고 판단되어도 clear_cart를 예외 없이 호출"하는 규칙이 없었음 | 프롬프트에 강한 규칙 추가 후 서로 다른 세션 3회 연속 재현 테스트로 확인 |

## 9-1. 시스템 프롬프트 최적화 (한국어 → 영어, 중복 제거)

사용자 요청으로 `ai_modules/llm/prompts.py`를 전면 재작성했다. 이 토크나이저 기준 한국어
지시문은 동일 의미의 영어보다 약 30~40% 더 많은 토큰을 쓰고(예: 42 vs 31 토큰), 이 프롬프트는
모든 턴마다 재전송되므로 언어를 영어로 바꾸고 중복 규칙을 통합했다. 메뉴명·옵션명·예시 발화 등
실제 데이터/패턴 매칭 대상은 그대로 한국어로 유지했다.

- 프롬프트 템플릿 토큰 수(카탈로그 제외, `o200k_base` 기준): **6,419 → 5,517 (약 14% 감소)**.
- 재작성 과정에서 `ChatPromptTemplate`이 시스템 프롬프트를 **두 번째로** `{변수}` 치환하는
  것을 놓치고 `{{}}`(이스케이프된 리터럴 중괄호)를 그대로 남겨 `KeyError: "" 변수 없음"` 으로
  전체 LLM 호출이 실패하는 버그를 만들었다가 직접 재현·수정함(중괄호를 문자로 쓰지 않고
  "괄호/중괄호/대괄호"를 말로 풀어 설명하도록 변경). 프롬프트를 만졌으면 반드시 실제
  `run_agent()` 호출까지 확인해야 하는 사례.

## 9-2. 결제 과정 GPT 동작 점검 (요청에 따른 재검증)

동일 세션에서 반복 재현 테스트로 결제 흐름을 검증했다.

- **회귀 발견 및 즉시 수정**: 프롬프트에 "이미 다음 질문이 뭔지 알고 있어도 도구 호출은
  생략하면 안 된다"는 보강 문단을 추가했더니, 오히려 "결제할게" 한 턴에 `start_checkout` +
  `points(no)` + `payment_method(cash)`까지 한꺼번에 호출해버리는 환각이 8회 중 5회
  발생함을 직접 재현. 원래(수정 전) 프롬프트는 같은 조건에서 8회 중 0회. 해당 보강 문단을
  즉시 제거해 8회 중 0회로 복구 확인.
- **temperature=0 실험**: 도구 호출 안정성을 높이려 `agent.py`의 `temperature`를 0.2→0으로
  낮춰봤으나, 오히려 위와 동일한 "한 턴에 전체 결제 단계를 임의로 완주"하는 환각이 8회 중
  7회로 악화됨을 확인하고 즉시 0.2로 되돌림. gpt-4o-mini에서는 temperature를 낮추는 것이
  이 시나리오에는 역효과였다.
- **잔존 한계(수정 완료 아님)**: "포인트 적립할게" 한 마디에 대해 실제로 `ui_action
  points(value=yes)` 도구를 호출하는 비율이 재현 테스트에서 25~67% 사이로 편차가 있었다.
  텍스트 응답("전화번호를 말씀해 주세요")은 매번 올바르게 나오지만, 그 응답에 필요한 도구
  호출 자체를 가끔 생략한다 — **이 문제는 이번 작업 이전부터 있던 것으로(원본 한국어
  프롬프트로도 동일하게 재현됨) 회귀가 아니라 gpt-4o-mini의 툴콜링 신뢰도 한계**로 판단.
  프롬프트 문구를 여러 방식으로 보강해봤으나 뚜렷한 개선을 확인하지 못했다. 근본적으로
  고치려면 프롬프트만으로는 부족하고, 서버 쪽에서 결제 단계 진행 상태를 별도로 추적해
  누락된 액션을 보정하는 코드 수준의 안전장치가 필요해 보인다(후속 과제로 남김).
- **★ 심각도 높은 잔존 한계 — "결제할게" 한 마디로 포인트/결제수단까지 임의로 완주해버리는
  환각**: 위의 회귀(보강 문단 추가)를 되돌린 뒤에도, 동일한 컨텍스트(카트 1건, 단순 발화
  "결제할게")를 8회 반복하면 사용자가 포인트·결제수단을 말하지 않았는데도
  `points(value=no)` + `payment_method(value=cash)`까지 같은 턴에 스스로 호출해버리는
  사례가 재현됐다. **이번 작업으로 만든 회귀가 아니라 이미 병합되어 있던 원본 프롬프트에도
  동일 조건(주문유형 dine-in)에서 8회 중 4회 재현됨을 직접 확인** — 즉 오늘 작업 이전부터
  존재하던 gpt-4o-mini 툴콜링 신뢰도 문제다. 실제 키오스크에서는 고객이 포인트/결제수단을
  말하지 않았는데 AI가 마음대로 "현금 결제"로 확정해버릴 수 있다는 뜻이라 비즈니스 리스크가
  있다. 화면은 실제로는 매 단계 팝업이 뜨고 5초 타이머로만 자동 진행되므로 당장 오작동 결제가
  발생하진 않지만(사용자가 화면을 보면 잘못된 단계로 넘어간 걸 알 수 있음), 완전 음성 전용
  사용 시나리오에서는 위험하다. **후속 조치 필요**: 서버가 결제 단계 진행 상태를 직접
  추적해서, 한 턴에 사용자가 말하지 않은 단계까지 건너뛴 액션은 무시/거부하는 코드 수준
  가드가 프롬프트 보강보다 확실한 해법으로 보인다.

## 10. 알려진 한계 / 검증하지 못한 부분

- **실제 마이크 음성 인식**: 이 환경에는 실제 음성 입력 장치가 없어, STT는 텍스트를 직접
  `/ai_modules/llm`에 주입하는 방식으로 LLM 판단 로직만 검증했다. Whisper의 실제 음성 인식
  정확도 자체는 실기기에서 재확인이 필요하다.
- **"OO 하나만 빼줘"(수량 2개 이상 중 1개)의 해석**: 상황에 따라 `remove_item`(줄 전체 삭제)
  또는 `update_item_options`(수량 1 감소)로 처리되는 것이 관측됨 — 둘 다 한국어 "빼줘"의
  합리적 해석 범위 안에 있으나, 정확히 "수량만 1개 줄이는" 의도인지는 케이스마다 다를 수
  있어 프롬프트에 더 명확한 규칙(예: 남은 수량이 있으면 항상 update_item_options 우선)을
  추가하는 후속 개선을 고려할 만하다.
- **"치즈버거 단품 두 개" 요청 시 치즈스틱이 같이 담긴 사례**: 1회 관측, 재현 조건 특정 못함.
  RAG 검색(`search_menu`)이 관련 없는 항목까지 후보로 반환하는 경향과 연관 가능성 — 후속
  모니터링 필요.
- **Arduino/물리 장치 실제 연동**: 실제 하드웨어가 없어 백엔드 시뮬레이션 응답까지만 확인.
  실제 시리얼/네트워크 연동은 하드웨어 준비 후 별도 검증 필요.
- **결제(PG) 실제 연동**: 카드/현금/간편결제 전부 결제 자체는 항상 성공 처리(시뮬레이션)이며
  실제 PG사 연동 여부는 검증 대상이 아니다.
- **결제 중 "포인트 적립할게" 단계의 도구 호출 누락**: 9-2 참고. 텍스트 응답은 항상 정상이나
  `ui_action points` 호출 자체가 가끔(재현 테스트 기준 25~67%) 생략됨. 화면이 안 넘어가면
  사용자가 한 번 더 말하면 대부분 정상 진행되지만, 근본 해결은 서버 측 상태 추적이 필요.
